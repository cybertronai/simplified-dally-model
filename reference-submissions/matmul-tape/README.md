# Reference submission: tape-driven matmul (tape-v0 proposal)

**Status: PROPOSAL, pending discussion in
[#2](https://github.com/cybertronai/simplified-dally-model/issues/2).** This is
the reference matmul submission Yaroslav asked for, built against the
**proposed** tape-and-core contract
([`instruction-sets/tape-v0/`](../../instruction-sets/tape-v0/)). Every
assumption that contract marks open is flagged here rather than silently
resolved.

What it is: a hand-written reference, not a searched or optimized submission.
Parameterized `C = A x B` over wrapping 8-bit cells, expressed as a **bounded
checkable schedule**: named operands, static sizes, straight-line ops
(`mul`/`add` only, so it is a plain v0 program under the tape profile). No
runtime recursion, no search, no data-dependent control flow. The schedule is
the scored artifact; this submission contains only the checked-in schedules
and their lowered IR forms.

## Files

The submission is data-only: the checked-in artifacts are the whole
submission, no scripts included.

- `matmul_4x4.schedule.json` / `matmul_4x4.ir` — the worked 4x4 instance.
- `matmul_2x2.schedule.json` / `matmul_2x2.ir` — the 2x2 paper instance.

The schedules are hand-checkable: straight-line `mul`/`add` op lists over
named operands with static sizes, so the arithmetic can be read off and
checked by hand against the layout below.

## Schedule shape

Row-major layout: `A[i][k]` at cell `1 + iN + k`, `B[k][j]` at cell
`N^2 + 1 + kN + j`, `C[i][j]` at cell `2N^2 + 1 + iN + j`, one shared product
scratch cell. Tape events, in order: `2N^2` `external_tape_read`s (all of A,
then all of B, row-major), then `N^2` `external_tape_write`s (C, row-major).
Ops: `N^3` `mul` + `N^2(N-1)` `add`; the `k=0` product writes `C[i][j]`
directly, so no constant materialization is needed and v0 suffices.

For 4x4: 32 tape-in bytes, 16 tape-out bytes, 112 ops (64 `mul`, 48 `add`).

## Verification (both existing executors, byte-exact)

The checked-in `.ir` forms run directly under the repo's own executors: the
Python reference executor (`mask_sparse_parity.py`) and the Rust executor
(`cybertronai/dally-eval`). Both were checked against a numpy wrapping-8-bit
ground truth, and the two referees agree with each other byte-for-byte (the
Rust `run` fixture's expected bytes are generated by the Python executor):

```
[python] semantic parity vs numpy: PASS (64 instances)
[python] static cost = 1316 (matches schedule fold)
[rust]   verify/cost agree with python: cost = 1316
[rust]   run: instances 64  width 32  static_cost 1316  correct 64/64 (100.00%)
BYTE-EXACT AGREEMENT: PASS (python <-> rust <-> numpy)
```

Same PASS for the 2x2 instance (cost 84).

## Cost breakdown (L1 wire-energy model)

Cell-read charge is the L1 wire length `ceil(sqrt(addr))`; tape bytes are flat
`T_read`/`T_write` per the tape-v0 proposal (default 1 each, **proposal
constant, not agreed**). Two totals are reported because the
**tape-write-vs-legacy-output-read billing question is open** (see the event
table in tape-v0): does `external_tape_write`'s charge *replace* the legacy
output-cell read (variant a) or *stack on top of it* (variant b)? This
submission does not pick a side.

4x4 worked instance:

| event | count | charge each | subtotal |
|-------|------:|-------------|---------:|
| operand cell reads (`mul`/`add` fetches) | — | `ceil(sqrt(addr))` | 1208 |
| legacy output-cell reads | 16 | `ceil(sqrt(addr))` (33..48 → 6..7) | 108 |
| `external_tape_read` bytes | 32 | `T_read` = 1 (proposed) | 32 |
| `external_tape_write` bytes | 16 | `T_write` = 1 (proposed) | 16 |

| total | value |
|-------|------:|
| legacy executor static cost of the lowered form | 1316 |
| variant (a) tape-write replaces output read | 1208 + 32 + 16 = **1256** |
| variant (b) tape-write stacks on output read | 1316 + 32 + 16 = **1364** |

2x2 instance: operand reads 69, output reads 15, tape-in 8, tape-out 4;
legacy 84; variant (a) **81**; variant (b) **96**.

Notes for the #2 discussion, visible in these numbers:

- The naive schedule re-reads A and B cells heavily (operand reads dominate).
  Writes are free, so a cheaper submission could stage copies at low
  addresses first; that optimization is deliberately **not** done here. A
  reference should be legible and obviously correct, not cheap.
- The gap between variants (a) and (b) is exactly the output-read subtotal
  (108 for 4x4), so the open billing question is worth 8.6% of this
  submission's total; on output-heavy kernels it would dominate.
- Executor delta: neither executor has the tape ops. The lowered form is what
  runs today (tape read → input placement in order; tape write → declared
  output). Byte-exact execution is verified on the lowered form; the tape
  ledger is the contract's add-on. Adding `external_tape_read/write` to both
  executors is the delta tape-v0 requires.
